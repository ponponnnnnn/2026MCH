長照 AI 陪伴 — 架構圖（現況版）

2026-09-20 決定：通話排程要做、一切以 App 為主、響鈴走 FCM 來電畫面（推翻 v2_mvp 原本「不做 Agent 主動開口／FCM」）。所以主要入口是「後端排程 → FCM → 長輩手機跳出小幫手來電 → 接聽就開始聊」，長輩自己按按鈕降為次要。每個框右上角標狀態：「✓ 已串」＝程式寫好、離線檢查通過；「◐ 實作中」＝正在寫；這台機器沒有 API key 與 Firebase 憑證，還沒打過任何一通真的電話、也還沒真的響過一次。滑過任一個框會亮出跟它相關的線。

◐ 正在寫（完成並驗證後這張卡會更新）

  • 後端通話排程：/jobs/call-schedule、/demo/ring、/devices/register、FCM 推播、callAttempts、晚報加「未接來電」。
  • Flutter：FirestoreRepository（照網頁版的查詢移植）、FCM 接收、「小幫手來電」畫面、接聽自動開始通話。

✗ 還沒串起來的

  • Firebase Android App 註冊：等 firebase login。沒有它，FCM 與 App 讀 Firestore 都跑不起來（App 會繼續走假資料）。
  • ICOPE 對齊：認知、行動／跌倒、視力、聽力四項完全沒問（見 TZZ/standards）。
  • GCP 兩個排程、種子資料、firestore.rules。

△ 串了但沒驗過的

  • 這台機器沒有 GEMINI_API_KEY、沒有 Firestore／Gmail／FCM 憑證：語音通話、7 個工具、通話摘要、晚報、寄信、推播都沒有真的跑過。
  • 不確定的點：Live API 接不接受這 7 個工具宣告、gemini-3.8-live 這個 ID、briefing 查詢要不要建索引、約 2900 字的 prompt 模型照不照做、模擬器收不收得到高優先 FCM。

跟 v5 的差異

  • 通話排程從「規劃中」變成主要入口；新增「FCM 推播 → 來電畫面」這一段；長輩按按鈕降為次要。
  • Firestore 多了 callWindows、fcmTokens、callAttempts；WebSocket 多了 attemptId。
  • 家屬輸出以 Flutter 為主；網頁版保留給跑不動 App 的組員測試。
